## Last Few Weeks (2026/05/11-2026/06/08)

## 1. Hybrid-EP scan optimizations landed for dense top-k routing

Continued the E=2304, topk=36, EP72/NVL72 Hybrid-EP optimization work, with the main recent progress on scan overhead for dense routing.

- Added dense local-expert and rank-bitset optimizations in the Hybrid-EP scan path.
- With scan optimizations and dense routing map support combined, the E=2304 case now reaches about **400 TFLOP/s**, up from about **320 TFLOP/s** in the last report.
- In isolated NVL72-like scan benchmarks, the no-permute-fusion E=32/topk=36 `512/108` template improved from about 526 us to about 332 us after the rank-bitset work.
- Rejected a warp-pruning variant after it showed mixed/regressing results; the simpler bitset path is the robust improvement.

## 2. TE and MCore dense routing map work progressed

Worked through the TE/MCore plumbing needed to carry compact `[T, K]` top-k indices instead of only the sparse bool `[T, E]` routing map.

- TE fused-router paths now support dense selected-index output and matching backward entry points.
- Dense route launch behavior was aligned with upstream radix/naive fallback policy, so large expert-count cases fall back instead of failing.
- MCore detects whether TE and the selected dispatcher backend support dense routing, then enables it only for compatible DeepEP/HybridEP cases.

## 3. TE fused-router deep optimization PR is up

Opened TE fused-router deep optimization PR: [NVIDIA/TransformerEngine#3012](https://github.com/NVIDIA/TransformerEngine/pull/3012).

This PR optimizes fused-router forward/backward kernels beyond the initial radix work in PR #2821:

- Fused preprocess/backward loops and reduced shared-memory pressure.
- Added async loading, persistent-grid sizing, packed radix histograms, and compile-time score-function dispatch.
- On B300, large-expert cases improved substantially; for example softmax topk backward at 2304/36 improved from about **543 GB/s** to about **2766 GB/s**, while small topk paths keep the simple kernel to avoid regressions.

## 4. Other Hybrid-EP explorations clarified what not to pursue

Explored several Hybrid-EP alternatives to answer open questions from the last update.

- Direct dispatch/permute was profiled and ruled out for H=512, topk=36: it amplifies NVLink writes by writing each token once per selected expert instead of once per destination rank.
- Fused dispatch+permute can be tuned to roughly match or slightly beat standalone, but fused combine+unpermute remains slower because combine is a pull/G2S read path and unpermute serializes behind produced chunks.
- Current practical recommendation for latent H=512 remains the non-fused standalone path, with scan/dense-routing optimizations as the main near-term wins.

## 5. End-to-end Qwen benchmark runs show gains on established recipes

Ran end-to-end GB200 benchmarks on more established Qwen recipes and model proxies, using median `TFLOP/s/GPU` from post-warmup job metrics as the headline number. Summary slides are available [here](https://nvidia-my.sharepoint.com/:p:/p/hhanyu/IQD-EIRxWvDNTosqlRe2Z9AxAZvdVQjg9Ofi0g9ThPo0DKI?e=0JZtBg).

- `2604base-hepS2F2` combines TE PR #3012, dense routing map support, Hybrid-EP dense routing/scan optimizations, and dispatch/combine sparse optimizations.
- Qwen3.5 Sparser 40B, EP72, paged stash + 1f1b: **300.5 to 389.6 TFLOP/s/GPU**, **+29.7%** over `2604base`.
- Qwen3 Sparser 80B, EP64, paged stash + 1f1b: **165.1 to 252.7 TFLOP/s/GPU**, **+53.1%** over `2604base`.
- Qwen3.5-397B proxy runs also show gains, with the sparser proxy reaching **826.8 TFLOP/s/GPU** on `hepS2F2` + paged stash + 1f1b.
